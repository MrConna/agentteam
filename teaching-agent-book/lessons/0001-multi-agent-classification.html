多 Agent 协作的分类框架

Lesson 1 · 15 min · 基于《深入理解 AI Agent》第 10 章

当你已经不是第一次在终端间切换——把任务派给 claude:1、codex:2、agy:3——你就已经在做多 Agent 协作了。问题是：你的协作方式有名字吗？你知道还有哪些选项吗？

本书第 10 章给出了一个简洁而有力的分类框架，只有两个维度：

  1. 上下文是否共享
  2. 协作拓扑（控制权与信息的流动结构）

这节课把它们一一拆开，直接映射到你正在做的 AgentTeam 上。

维度一：上下文是否共享

这是最基础的架构决策。用书里的话说：

共享上下文 = 后一个 Agent 继承前一个的完整对话历史，就像围坐一桌讨论。
不共享上下文 = 每个 Agent 独立工作，通过文件/消息交换信息，就像不同部门协作。
直接映射到 AgentTeam
你的 tmux send-keys 协调方式——leader 给各窗口发独立任务，各 session 独立执行、通过 tmux 输出交换结果——就是典型的不共享上下文模式。而 intercom 双向通信或 delegate 子 agent 则是介于两者之间。

选哪个？书里给了一张表格作为选型检查表：

选择依据共享上下文不共享上下文
子任务数量少（2-3 个角色）多（需要并行处理）
上下文窗口足以容纳所有角色信息单窗口装不下
并行度串行为主可大规模并行
信息隔离不需要需要（如安全审查）
成本预算单轨迹接力，Token 累积总 Token 通常高出数倍
经验法则：若预期累计上下文会超过窗口的 50%，应不共享。多数实际系统采用"阶段切换式"——前几个 Agent 共享，到信息饱和点后切换为不共享 + 显式 handoff。

维度二：协作拓扑

一旦选择不共享上下文，"信息如何流动、由谁协调"就成为必须显式设计的问题。书里给出三种拓扑，按复杂度递增：

1. 对等协作 (Peer Collaboration)

2-3 个 Agent 平等交互，形成迭代改进循环——就像写论文时一个人起草、另一个人批注修改。不加新信息的纯辩论通常无效，但引入外部反馈（代码执行结果、截图审查）时效果显著。

AgentTeam 对照：你把一个任务切分成"codex 实现、claude review、agy 测试"——这就是对等协作。关键是要确保每个环节引入了新信息（测试结果、审查意见），而不是三个 Agent 对着同一段文本各自输出。

2. 管理者模式 (Orchestration)

一个中心化的 Manager Agent 负责任务规划和调度，多个子 Agent 各负责特定子任务。这是目前工程中最常用的模式。

AgentTeam 对照：你（leader）就是这个 Manager。你负责拆任务、分配给各窗口、监控进度、汇总结果。书中的管理者模式给了你一套理论语言来描述你已经在做的事。

3. 去中心化模式 (Decentralized)

没有运行时的中心控制者，Agent 之间像人类一样互相沟通。适合 Agent 数量多、动态发现彼此的复杂场景。

值得关注：当你需要 10 个以上的 Agent 协作时，去中心化模式就变得有吸引力了——管理者会成为瓶颈。这是 AgentTeam 未来可能的演进方向。

什么时候多 Agent 真的优于单 Agent？

书里给出了一个清晰判断：协作过程是否引入了单个 Agent 在生成时无法获得的新信息？

协作模式是否引入新信息效果
同一模型自我审查❌ 否通常无效
不同 Agent 辩论同一段文本❌ 否与单 Agent 持平
Reviewer 使用测试执行结果审查代码✅ 是显著提升
Reviewer 查看渲染截图审查前端代码✅ 是显著提升
Reviewer 使用外部工具验证事实✅ 是显著提升
成本警告：Anthropic 曾披露其多 Agent 研究系统的 Token 消耗约为普通对话的 15 倍！Token 用量本身就能解释约 80% 的性能差异。一个调校得当的单 Agent 往往更划算。
