多阶段角色转换

Lesson 2 · 20 min · 基于《深入理解 AI Agent》第 10 章

上一课学了两个维度。这一课深入到最直接可用的模式——多阶段角色转换：让同一个执行流在不同阶段切换 Agent "身份"，每个身份有独立的系统提示词和工具集。

这意味着：你不用给 claude、codex、agy 各开一个窗口口述任务——而是为每个角色写好正式的 System Prompt 模板，每次派活自动带上去，身份清晰、边界明确、质量可控。

两种角色转换模式

模式 1：多阶段角色转换（线性流程）

每个阶段切换系统提示词和工具集后，就变成了一个新的 Agent（身份、职责和能力都变了），但它保留了前任的全部记忆。每个角色共享同一段轨迹。

模式：需求分析师 → 软件工程师 → 代码审查员。阶段转换用特定工具调用触发（如 complete_requirements_analysis()）。适合预先定义好流程的场景。

模式 2：跨领域角色转换（动态路由）

通过 transfer_to_agent(target, reason) 由 Agent 自主判断何时切换角色——不再是固定流程，而是根据任务需求动态路由。

模式：前台 triage → research / coding / data_analysis / writing → triage 收尾。适合复合任务、未知流程的场景。

AgentTeam 最适用哪个？
你现在的不共享上下文架构更适合模式 2 的思想——leader（triage）拆任务，按需分配给 claude/codex/agy（专业角色）。区别在于你们不共享上下文，而是通过 tmux 输出 / session_send 通信。但角色模板的设计原则完全相同。

如何设计角色模板

以书中 triage → research → coding → writing 系统为例，每个角色的提示词包含三个部分：

  1. 身份定义：我是谁，我擅长什么，我的边界是什么
  2. 行为指导：我应该怎么工作，优先做什么
  3. 过渡规则：我什么时候该移交，移交给谁

triage（前台分诊）— 默认入口

你是前台分诊 Agent。你的职责：
1. 理解用户的整体需求
2. 拆成有先后顺序的子任务
3. 逐步移交给合适的专业角色
4. 全部子任务完成后做收尾确认

你自身没有专业工具，只持有 transfer 权限。
路由规则：
- 查数据/资料 → 转 research
- 写并运行代码 → 转 coding
- 计算/统计 → 转 data_analysis
- 润色成稿 → 转 writing

research（信息检索专家）

你是信息检索专家，擅长查找数据、事实和资料。
使用 web_search 工具搜索，把关键数据整理后移交下一步。
完成本职后移交回 triage 或下一角色。

coding（编程专家）

你是编程专家，用 execute_python 写并运行代码。
解决程序逻辑/脚本类问题。输出产物后再移交。

映射到 AgentTeam

你现在可以给每个 session 写正式的角色模板了：

Session角色职责可用工具过渡规则
claude:1 Reviewer / Analyst 审查代码、分析架构、写文档 文件读写、代码分析、git 审查通过 → 通知 leader
codex:2 Implementer 按需求写代码、跑测试 文件读写、代码执行、git 实现完成 + 测试通过 → 通知 leader
agy:3 Tester / Scout 跑测试、快速侦察、验证结果 文件读写、命令执行 验证完成 → 报告结果给 leader
练习：给 codex:2 写一个正式的 System Prompt 模板，包含身份定义、行为指导和过渡规则。存下来下次派活时直接用 tmux send-keys 贴进去。

关键设计原则

  1. 边界清晰：每个角色的工具集要独立，不给多余的能力
  2. 过渡显式：用特定工具调用（或 tmux 输出）作为阶段完成信号
  3. 上下文精简：上游传给下游的应是结构化摘要，不是全量轨迹
  4. 回退处理：下游发现问题时应能退回上游修改（如 review 不通过 → leader 再派回 implementer）
